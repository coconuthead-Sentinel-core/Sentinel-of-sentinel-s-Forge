SECTION 1 — SECURITY ARCHITECTURE OVERVIEW
================================================================================

1.1  Security Philosophy

Sentinel Forge is designed under a defense-in-depth security philosophy.
Security controls are layered at multiple levels — transport, application,
authentication, authorization, and data — such that the failure of any single
control does not result in a complete security breach. The platform moved
from a CRITICAL security posture (hardcoded API keys, open CORS, no auth) to
a HARDENED security posture through a focused security sprint delivering
28 file changes and 2,181 lines of security-focused code additions.

2.1  STRIDE Methodology

The STRIDE threat model classifies threats into six categories:
  S — Spoofing (impersonating another entity)
  T — Tampering (modifying data or code)
  R — Repudiation (denying having performed an action)
  I — Information Disclosure (exposing information to unauthorized parties)
  D — Denial of Service (making service unavailable)
  E — Elevation of Privilege (gaining unauthorized access levels)

SECTION 3 — AUTHENTICATION FLOWS
================================================================================

3.1  REST API Authentication — JWT Bearer Token

  Step 1: Registration
    Client → POST /api/auth/signup
    Body: { "email": "user@domain.com", "password": "secure123",
            "display_name": "User Name" }
    Server: Validates email uniqueness, bcrypt-hashes password,
            stores user record in Cosmos DB
    Response: { "access_token": "...", "refresh_token": "...",
                "token_type": "bearer", "user": {...} }

  Step 2: Login
    Client → POST /api/auth/login
    Body: { "email": "user@domain.com", "password": "secure123" }
    Server: Fetches user by email (case-insensitive), bcrypt.verify(),
            issues new JWT pair
    Response: { "access_token": "...", "refresh_token": "...",
                "token_type": "bearer" }

  Step 3: Authenticated Request
    Client → GET /api/auth/me
    Headers: Authorization: Bearer <access_token>
    Server: get_current_user() dependency decodes JWT via python-jose,
            validates signature and expiry, loads user from DB
    Response: { "user_id": "...", "email": "...", "role": "user", ... }

  Step 4: Token Refresh
    Client → POST /api/auth/refresh
    Body: { "refresh_token": "..." }
    Server: Validates refresh_token, issues new access_token
    Response: { "access_token": "...", "token_type": "bearer" }

3.2  API Key Authentication

  Applicable To:  Operational endpoints requiring machine-to-machine auth
                  (cognition, sync, glyphs, stress test endpoints)

  Flow:
    Client → Any protected route
    Headers: X-API-Key: <configured_api_key>
    Server: api_key_guard() dependency validates against settings.API_KEY
    On success: Request proceeds
    On failure: HTTP 401 "Invalid or missing API key"

  Admin Flow:
    Client → Admin-tier route
    Headers: Authorization: Bearer <admin_jwt>
             X-API-Key: <configured_api_key>
    Server: admin_guard() verifies API key; RBAC verifies admin role
    Both checks must pass for request to proceed

3.3  WebSocket Authentication

  WebSocket Endpoint: /ws/sync

  Authentication Priority Order:
    1. Header: x-api-key (preferred for server-to-server)
    2. Query Parameter: ?api_key=<key> (for browser clients unable to set
       custom headers on WebSocket upgrade)

  Flow:
    Client → WebSocket upgrade request to /ws/sync
    Server: websocket_require_api_key() called before connection accepted
    If API key valid: WebSocket connection accepted; NDJSON stream begins
    If API key invalid/missing: HTTP 401 returned; connection rejected
    If production and key not configured: HTTP 401 "API key required"

  Post-Connection Message Format:
    { "type": "cog.intent",   "data": { ... } }   — cognitive intent update
    { "type": "sync.update",  "data": { ... } }   — tri-node state update

3.4  Token Security Properties

  Property                Value/Implementation
  ----------------------  --------------------------------------------------
  Algorithm               HS256 (HMAC SHA-256) via python-jose
  Secret storage          Environment variable; never in source code;
                          validated to be set in production mode
  Access token lifetime   Configurable via settings; default: short (hours)
  Refresh token lifetime  Configurable via settings; default: longer (days)
  Token payload claims    user_id, email, role, exp, iat
  Revocation              Stateless JWT; revocation via expiry or key
                          rotation (key rotation procedure: Section 5.3)
  Storage guidance        JWT stored in memory by client; NOT localStorage
                          (XSS risk); guidance in USER_GUIDE.md

4.3  RBAC Implementation Details

  The RBAC system is implemented as FastAPI dependency injection:

  # Example: User-tier route
  @router.post("/cog/process")
  async def process(
      data: ProcessRequest,
      user: User = Depends(require_role("user"))  # Tier 2 minimum
  ):

  # Example: Admin-tier route with dual control
  @router.post("/stress")
  async def stress(
      params: StressRequest,
      _: None = Depends(admin_guard),              # API key required
      user: User = Depends(require_role("admin"))  # Admin JWT required
  ):

  The require_role() dependency:
    1. Extracts Bearer token from Authorization header
    2. Decodes JWT via python-jose (HS256)
    3. Validates expiry (exp claim)
    4. Loads user from Cosmos DB via user_id claim
    5. Checks user.role >= required_role threshold
    6. Returns User object to route handler (or raises HTTP 403)

SECTION 6 — INCIDENT RESPONSE PROCEDURES
================================================================================

6.1  Incident Classification

  Severity    Definition                              Response SLA
  ----------  ------------------------------------    --------------------
  CRITICAL    Active breach, data exfiltration,       15 minutes to initial
              credential compromise, privilege        response; 1 hour to
              escalation confirmed                    containment
  HIGH        Suspected breach, auth bypass           1 hour to initial
              attempt, significant availability       response; 4 hours to
              impact (>30min outage)                  resolution
  MEDIUM      Security anomaly detected, rate         4 hours to initial
              limit exhaustion, suspected             response; 24 hours to
              credential stuffing                     root cause
  LOW         Security warning, minor config          24 hours to initial
              deviation, failed auth spike            response; 72 hours
                                                     to resolution

6.2  Incident Response Process

  PHASE 1 — DETECTION AND TRIAGE (0-15 minutes)
    1. Incident identified via:
       - Automated alert (ELK/CloudWatch rule on log patterns)
       - Security anomaly in Prometheus metrics
       - Customer report via VR Studios contact
       - Internal team discovery
    2. Initial severity classification (see 6.1)
    3. Incident ticket created; on-call engineering notified
    4. Incident Commander designated for CRITICAL/HIGH incidents

  PHASE 2 — CONTAINMENT (15 minutes - 4 hours)
    Security Incident:
      - If credential compromise: Rotate affected secrets immediately
      - If API key exposure: Revoke and reissue API key; update all deployments
      - If JWT signing secret exposed: Rotate secret; all tokens invalidated
      - If active exploit: Rate limit or block offending IPs
    Availability Incident:
      - Assess health endpoints (GET /api/healthz, GET /api/readyz)
      - Activate Gradio fallback if cognitive services unavailable
      - Enable MOCK_AI=true for degraded operation if Azure OpenAI offline
      - Scale Azure App Service if resource exhaustion confirmed

  PHASE 3 — INVESTIGATION (During/after containment)
    1. Review structured JSON logs for affected time window
    2. Identify affected request_ids, user_ids, and endpoints
    3. Determine attack vector or failure cause
    4. Assess data exposure scope (was PII accessed? billing data? credentials?)
    5. Preserve log evidence before rotation

  PHASE 4 — RECOVERY
    1. Restore service to normal operation
    2. Verify 40/40 test suite passes post-recovery
    3. Confirm health endpoints return healthy status
    4. Monitor metrics for 2 hours post-recovery for anomaly recurrence

  PHASE 5 — POST-MORTEM (within 48 hours for CRITICAL, 1 week for others)
    1. Timeline of events documented
    2. Root cause analysis completed
    3. Control gaps identified
    4. Remediation actions assigned with owners and due dates
    5. Post-mortem document stored in compliance evidence repository
    6. Risk register updated if new risk identified

6.3  Contact and Escalation

  Role                    Responsibility
  ----------------------  ---------------------------------------------------
  On-Call Engineer        First responder; initial containment
  Engineering Lead        Escalated for CRITICAL/HIGH incidents
  Operations              Infrastructure access; Azure Portal actions
  Legal/Compliance        Notification for data breach incidents (GDPR/CCPA

SECTION 9 — RATE LIMITER SPECIFICATION
================================================================================

9.1  Implementation Reference

  File:       /backend/core/security.py
  Class:      RateLimiter
  Algorithm:  Token Bucket

9.2  Token Bucket Algorithm Detail

  The RateLimiter class implements a token bucket per client IP address:

  Initialization:
    - bucket[ip] initialized with tokens = BURST (full bucket)
    - timestamp set to current time

  Per-Request Processing:
    1. Compute elapsed time since last request for this IP
    2. Calculate refill: elapsed_seconds × (RPM / 60) tokens added
    3. Cap tokens at BURST maximum
    4. If tokens < 1.0: raise HTTP 429 "Rate limit exceeded"
    5. Decrement tokens by 1.0
    6. Update bucket timestamp

  Parameters:
    RATE_LIMIT_ENABLED    Boolean; if False, limiter bypassed entirely
    RATE_LIMIT_RPM        Requests per minute sustained rate
    RATE_LIMIT_BURST      Maximum burst token count (allows short spikes)

  Storage:
    In-memory dict (self._buckets) indexed by IP string
    Note: Shared state within single process; does not persist across
    restarts or scale-out instances. For multi-instance deployment (Phase 4),
    replace with Redis-backed distributed rate limiter.

  Environment     RPM    Burst   Notes

  Development     Off    Off     RATE_LIMIT_ENABLED=false for unrestricted
                                 local testing
