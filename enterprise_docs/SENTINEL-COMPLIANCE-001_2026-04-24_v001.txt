SECTION 1 — DOCUMENT PURPOSE AND SCOPE
================================================================================

1.1  Purpose

This document provides a formal mapping of the Sentinel Forge Enterprise
Cognitive AI Platform to three major compliance frameworks:

  1. NIST AI Risk Management Framework (AI RMF) 1.0
     Published by the National Institute of Standards and Technology, January
     2023. Applicable to the AI-powered cognitive processing components of
     Sentinel Forge.

  2. SOC 2 Type II (System and Organization Controls)
     AICPA Trust Service Criteria framework. Applicable to Sentinel Forge's
     cloud-hosted infrastructure, security controls, and data handling
     practices.

  3. ISO/IEC 27001:2022 Information Security Management System
     International standard for information security management. Applicable
     to the information security posture of the platform and its operations.

1.2  Scope of Coverage

This compliance document covers:
  - Sentinel Forge backend platform (60 files, 8,217 lines of code)
  - 76 API routes (REST + WebSocket)
  - Azure cloud infrastructure (Azure App Service, Azure OpenAI, Azure Cosmos DB)
  - nginx reverse proxy and TLS configuration
  - Authentication and authorization subsystems (JWT, bcrypt, RBAC)
  - Rate limiting controls (token bucket, IP-based)
  - Billing subsystem (Stripe integration)
  - Glyphic protocol and cognitive processing engine
  - WebSocket real-time synchronization

1.3  Compliance Posture Summary

  Framework          Assessment Status    Maturity Level
  -----------------  -------------------  ---------------------------

SECTION 2 — NIST AI RISK MANAGEMENT FRAMEWORK 1.0
================================================================================

The NIST AI RMF 1.0 organizes AI risk management into four core functions:
GOVERN, MAP, MEASURE, and MANAGE. The following sections provide detailed
mapping of Sentinel Forge controls and practices to each function.

--------------------------------------------------------------------------------
2.1  GOVERN — Establishing Accountability and Policies
--------------------------------------------------------------------------------

The GOVERN function establishes organizational accountability for AI risk
management, creates policies and procedures, and ensures that AI risk
considerations are embedded in the organization's culture and practices.

2.1.1  Organizational Accountability Structure

  GOVERN 1.1 — Policies, Processes, Procedures, and Practices

  Sentinel Forge implements organizational accountability through the following
  structures:

  (a) Engineering Governance
      The Engineering team maintains ownership of all technical controls,
      security architecture, and AI model integration decisions. The Master
      SDLC document (SENTINEL-SDLC-MASTER-001) establishes the formal
      governance framework.

  (b) Phase Gate Reviews
      Each major development phase includes a formal gate review assessing
      AI risk, security posture, and quality before advancement. Phase 1, 2,
      and 3 have each completed gate reviews with 100% test pass requirements.

  (c) Documented AI Use Policy
      The platform's Terms of Service (/legal/terms.html) includes 16 sections
      defining acceptable use of the AI cognitive platform, intellectual
      property provisions, and user accountability for AI-generated outputs.

  GOVERN 1.2 — Accountability and Roles

  Role                    AI Accountability
  ----------------------  ------------------------------------------------------
  Engineering Lead        Owns AI model selection, integration architecture,
                          Azure OpenAI configuration, and prompt design
  Operations              Owns AI infrastructure uptime, monitoring, and
                          incident response for AI-related outages
  Product                 Owns AI feature roadmap, pilot customer requirements,
                          and evaluation of AI output quality
  Legal/Compliance        Owns AI use policy, data processing agreements with
                          Azure (data processor), and regulatory alignment

  GOVERN 2.1 — Organizational Risk Tolerance

  Sentinel Forge's AI risk tolerance is classified as MODERATE. The platform:
    - Uses Azure OpenAI (Microsoft-managed model) rather than custom-trained
      models, reducing model development risks
    - Implements Gradio fallback UI for degraded-mode operation when AI
      processing is unavailable
    - Limits AI processing scope to: cognition, intent classification,
      memory retrieval, and glyphic sequence interpretation
    - Does not use AI for high-stakes autonomous decisions (medical, legal,
      financial determinations)

  GOVERN 3.1 — Organizational Teams Are Committed to Risk Management

  Evidence of commitment:
    - 3 engineering sprints delivered to harden platform from prototype to
      production (28 files changed, 2,181 lines added)
    - Security posture elevated from CRITICAL gaps to HARDENED state
    - 22 new tests added to support security and compliance controls
    - Formal documentation suite created (7 enterprise documents)

2.1.2  4-Tier Role-Based Access Control

The platform implements a 4-tier RBAC system as a primary GOVERN control,
enforcing the principle of least privilege across all API access.

  Tier        Role        Description                    Access Level
  ----------  ----------  ----------------------------   -------------------
  Tier 1      Viewer      Read-only access to public     Lowest; read-only
                          platform data and metrics
  Tier 2      User        Standard authenticated user    Standard cognitive
                          operations; chat, threads,     API access
                          seeds, glyphs
  Tier 3      Operator    Enhanced access for            Elevated; rule
                          operational management;        management, memory
                          cognitive rule management      operations
  Tier 4      Admin       Full administrative access;    Highest; all routes
                          user management, system        including destructive
                          configuration, destructive     operations
                          operations

  Implementation:
    - RBAC tiers are enforced as FastAPI dependency injection on each route
    - admin_guard() in security.py enforces API key requirement for Admin
      operations regardless of JWT claim
    - All 76 routes have RBAC requirements explicitly applied
    - 8 automated tests in test_rbac.py verify RBAC enforcement

2.4  MANAGE — Responding to and Recovering from AI Risks
--------------------------------------------------------------------------------

The MANAGE function implements controls to respond to and recover from
identified AI risks.

2.4.1  Incident Response for AI Events

  Incident Type           Response Procedure
  ----------------------  --------------------------------------------------
  Azure OpenAI outage     1. Automated health probe detects /api/cog/status
                             failure within 60 seconds
                          2. On-call operations notified via structured log
                             alert (ELK/CloudWatch rule)
                          3. Gradio fallback UI activated (degraded mode)
                          4. MOCK_AI=true flag set for continued operation
                          5. Azure status page monitored for recovery ETA
                          6. Full restoration tested before fallback removed

  AI output quality       1. Anomalous output detected via evaluation
  degradation event          framework or customer report
                          2. Engineering reviews evaluation metrics and
                             Prometheus intent/resonance data
                          3. Azure OpenAI model version checked against
                             last known good configuration
                          4. If model version changed: document delta and
                             update evaluation baselines
                          5. If persistent degradation: engage Azure support

  Glyphic injection       1. Security alert triggered by WAF or log pattern
  attempt detected           matching on /api/glyphs/* routes
                          2. Offending IP rate-limited or blocked
                          3. Security review of injection patterns
                          4. Input validation rules updated if new pattern
                             identified
                          5. Incident documented in security log

2.4.2  Rate Limiting as AI Availability Control

  The token bucket rate limiter in security.py (class RateLimiter) directly
  manages the risk of AI availability disruption from request flooding:

  Control Parameter       Configuration               Effect
  ----------------------  --------------------------  -------------------------
  settings.RATE_LIMIT_RPM  Requests Per Minute limit   Prevents Azure OpenAI
                           (configurable via env)      quota exhaustion per IP
  settings.RATE_LIMIT_BURST Burst token allowance      Permits legitimate
                           (configurable via env)      traffic spikes without
                                                       triggering limits
  settings.RATE_LIMIT_ENABLED On/off flag              Allows emergency
                           (production: always on)     disable if needed

  When rate limit is exceeded:
    HTTP 429 "Rate limit exceeded" returned immediately
    No Azure OpenAI call is made (token preserved)
    IP bucket resets at configured RPM rate

2.4.3  API Key Guard as Access Control

  The api_key_guard() function in security.py implements the primary API
  access control for non-JWT routes:

  Scenario                    Behavior
  --------------------------  ------------------------------------------------
  Production + key set +      Request ALLOWED
  valid X-API-Key header
  Production + key set +      HTTP 401 "Invalid or missing API key"
  invalid/missing key
  Production + key NOT set    HTTP 503 "Server misconfigured" (security fail-
                              safe; does not allow unauthenticated access)
  Development + key NOT set   Request ALLOWED (developer convenience mode)

SECTION 3 — SOC 2 TYPE II ALIGNMENT

3.1  SOC 2 Trust Service Criteria Overview

SOC 2 is organized around five Trust Service Criteria. The following sections
document Sentinel Forge's alignment to each criterion.

--------------------------------------------------------------------------------
3.1.1  Security (CC6 — Logical and Physical Access Controls)
--------------------------------------------------------------------------------

  CC6.1 — Logical access security software, infrastructure, and architectures
  have been implemented to support (1) identification and authentication of
  authorized internal and external users; (2) restriction of authorized
  internal user access; and (3) prevention and detection of unauthorized access.

  Sentinel Forge Controls:

  Control                     Implementation
  --------------------------  --------------------------------------------------
  User Identification         Email-based identity; enforced unique email
                              registration via POST /api/auth/signup
  Authentication              JWT HS256 tokens via python-jose library;
                              access_token + refresh_token issued on login;
                              Bearer token required on all protected routes
  Password Security           bcrypt hashing (salt factor configurable);
                              passwords never stored in plain text; never logged
  Token Expiry                JWT access tokens have configurable expiry;
                              refresh tokens support rotation
  API Key Authentication      X-API-Key header enforcement on operational
                              endpoints; admin_guard() for destructive routes
  WebSocket Authentication    websocket_require_api_key() enforces API key
                              via header (x-api-key) or query param (api_key)
                              for all WebSocket connections
  4-Tier RBAC                 Role-based access restricts unauthorized
                              elevation; each route has explicit role
                              requirement enforced as FastAPI dependency

  CC6.6 — The entity implements logical access security measures to protect
  against threats from sources outside its system boundaries.

  Control                     Implementation
  --------------------------  --------------------------------------------------
  TLS 1.2/1.3                 All traffic encrypted in transit via nginx;
                              older TLS versions rejected
  CORS lockdown               Allowlist-only CORS configuration; open CORS
                              was identified and closed during security audit
  Security headers            nginx injects: HSTS (max-age 31536000),
                              CSP (restrictive), X-Frame-Options DENY,
                              X-XSS-Protection, X-Content-Type-Options
  Rate limiting               Token bucket per IP; HTTP 429 returned on
                              excess; protects against external abuse

  CC6.7 — The entity restricts the transmission, movement, and removal of
  information to authorized internal and external users.

  Control                     Implementation
  --------------------------  --------------------------------------------------
  Data in transit             TLS 1.2/1.3 mandatory; no plaintext HTTP
  Data at rest                Azure Cosmos DB encryption at rest (AES-256,
                              Microsoft-managed keys)
  JWT scope control           Tokens scoped to authenticated user identity;
                              no cross-user data access possible

  CC6.8 — The entity implements controls to prevent or detect and act upon
  the introduction of unauthorized or malicious software.

  Control                     Implementation
  --------------------------  --------------------------------------------------
  Dependency management       requirements.txt pins dependencies; no wildcard
                              version specifications for security packages
  Input validation            Pydantic schema validation on all request bodies;
                              type enforcement prevents injection via inputs
  No eval/exec usage          No dynamic code execution in application code
